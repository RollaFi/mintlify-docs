## Overview

Accept payments from mobile money wallets across Africa. Most wallets send the customer a prompt on their phone, which they approve with their mobile money PIN. Some finish on the wallet's own page instead — see [Payment flows](#payment-flows).

**Currencies:** `GHS` (Ghana) and `XOF` (Senegal) today; `KES` and `ZMW` where enabled. The API does not restrict the currency itself — which ones you can charge depends on the mobile money processors enabled on your account. Contact support to confirm what is enabled for you.

<Warning>
  The wallet to debit goes in **`mobileMoney.phone`**, not `customer.phone`. `customer.phone` is stored as a contact detail and is never sent to the processor — a request without `mobileMoney` is rejected with a 400.
</Warning>

## Wallets by market

In **XOF markets, `mobileMoney.provider` is required** and must be one of the identifiers below. It selects both the wallet and the market, so there is nothing else in the request that says which country the payment is for.

| Market | Wallet | `provider` | Flow |
|--------|--------|-----------|------|
| Senegal | Orange Money | `orange-senegal` | Prompt, after a code the customer generates |
| Senegal | Wave | `wave-senegal` | Redirect to Wave |
| Ghana | MTN, Vodafone, AirtelTigo | `MTN`, `VODAFONE`, `AIRTELTIGO` | Prompt |

Rather than hardcoding this table, call [List Mobile Money Providers](/api-reference/mobile-money-providers) — it returns the wallets currently live in a market, and tells you which flow each one uses.

<Note>
  Benin and Togo are not live yet. Charging one of their wallets returns a `503` naming the wallet — call [List Mobile Money Providers](/api-reference/mobile-money-providers) to see what is live rather than assuming from this table, since markets are enabled without a change to these docs.
</Note>

## Amounts in XOF

The West African CFA franc has no subunit — there is no such thing as half a franc. **Amounts must be whole numbers**, and a decimal is rejected rather than rounded:

```json
{ "success": false, "message": "amount: XOF has no subunit — amount must be a whole number. Received 1000.5" }
```

Naira, cedis and every other currency are unaffected and still take decimals as before.

## Authentication

All requests must include your secret API key in the Authorization header:

```
Authorization: Bearer sk_live_your_secret_key
```

<Note>
  Use `sk_test_*` keys for testing and `sk_live_*` keys for production.
</Note>

## Request Body

<ParamField body="reference" type="string">
  Optional custom transaction reference. If not provided, a unique reference will be auto-generated (e.g., `TXN_gGbEEvK25eVgmgrf`). Must be globally unique across all transactions.
</ParamField>

<ParamField body="amount" type="number" required>
  The payment amount (e.g., 100 for 100 units of the currency)
</ParamField>

<ParamField body="currency" type="string" required>
  Three-letter ISO currency code, e.g. `GHS`, `XOF`, `KES`. Must be a currency your enabled mobile money processors support. `XOF` amounts must be whole numbers.
</ParamField>

<ParamField body="channel" type="string" required>
  Must be `mobile_money`
</ParamField>

<ParamField body="mobileMoney" type="object" required>
  The wallet being debited. **Required for this channel** — omitting it returns a 400.
  <Expandable title="properties">
    <ParamField body="phone" type="string" required>
      The mobile money wallet number, including country code (e.g., `233241234567` for Ghana, `254712345678` for Kenya). Max 20 characters.
    </ParamField>
    <ParamField body="provider" type="string">
      Which wallet to debit — see [Wallets by market](#wallets-by-market). **Required in XOF markets**, where it also selects the country. Optional in Ghana, where the processor resolves it from the number. Max 50 characters.
    </ParamField>
    <ParamField body="customerCode" type="string">
      **Required for `orange-senegal`.** Orange has the customer generate a 6-digit code on their handset before the payment is charged — they dial `#144#391#` and enter what comes back. Without it the request is rejected. No other wallet uses this.
    </ParamField>
  </Expandable>
</ParamField>

<ParamField body="customer" type="object" required>
  Customer information
  <Expandable title="properties">
    <ParamField body="email" type="string" required>
      Customer's email address
    </ParamField>
    <ParamField body="name" type="string">
      Customer's full name
    </ParamField>
    <ParamField body="phone" type="string">
      Contact phone number. **Not used to debit the wallet** — put that in `mobileMoney.phone`. Max 20 characters.
    </ParamField>
  </Expandable>
</ParamField>

<ParamField body="callbackUrl" type="string" required>
  URL to redirect the customer after payment completion. Query parameters `reference` and `status` (successful/failed) will be appended.
</ParamField>

<ParamField body="description" type="string">
  Optional description for the payment (max 500 characters)
</ParamField>

<ParamField body="metadata" type="object">
  Additional key-value pairs to attach to the transaction (e.g., order ID)
</ParamField>

## Response

<ResponseField name="success" type="boolean">
  Indicates if the request was successful
</ResponseField>

<ResponseField name="message" type="string">
  Response message
</ResponseField>

<ResponseField name="data" type="object">
  <Expandable title="properties">
    <ResponseField name="reference" type="string">
      Unique transaction reference or your custom reference if provided
    </ResponseField>
    <ResponseField name="status" type="string">
      `pending` — a prompt is on the customer's phone and you are waiting for them to approve it. `requires_action` — the customer has to finish on the wallet's own page, at `payment_url`.
    </ResponseField>
    <ResponseField name="payment_url" type="string">
      Present only when `status` is `requires_action`. Send the customer here to complete the payment. Returning from it does **not** mean the payment succeeded — confirm with [Verify Transaction](/api-reference/verify-transaction) or wait for the webhook.
    </ResponseField>
  </Expandable>
</ResponseField>

<Note>
  The initiate response is intentionally minimal. To see the decline reason, AVS/CVV results or any other detail, call [Verify Transaction](/api-reference/verify-transaction).
</Note>

## Payment flows

Which one you get depends on the wallet, and the response tells you: `pending` means a prompt is already on the customer's phone, `requires_action` means you have somewhere to send them.

### Prompt on the phone

Ghana's wallets, and Orange Senegal once the code is supplied.

1. **The prompt arrives.** Nothing to redirect to — it appears on the handset on its own.
2. **The customer approves it** with their mobile money PIN.
3. **You find out** by [webhook](/api-reference/webhooks), or by polling [Verify Transaction](/api-reference/verify-transaction) every 3–5 seconds until `status` is `successful`.

### Code first, then prompt

Orange Senegal only. Before you charge, the customer dials **`#144#391#`** on their handset and Orange returns a 6-digit code. Collect that, send it as `mobileMoney.customerCode`, and from there it behaves like any other prompt.

Ask for the code on the same screen as the phone number — a customer who has already left to dial a USSD string will not reliably come back.

### Redirect to the wallet

Wave Senegal. The response carries `payment_url`; send the customer there and they finish in the Wave app or on Wave's site.

<Warning>
  The customer coming back from `payment_url` does not mean they paid. Confirm with the webhook or Verify Transaction before releasing anything.
</Warning>

## Expiry

A mobile money payment stays open for a limited window — **15 minutes in XOF markets**, longer elsewhere. If the customer never approves it, the transaction is marked **`failed`** with a `response_code` of `EXPIRED`, which is how you tell an abandoned payment from a declined one on [Verify Transaction](/api-reference/verify-transaction).

Start a new transaction rather than retrying; a reference cannot be reused.

Webhooks fire on `pending`, `successful` and `failed`. There is no separate expiry event — an expired payment is a `payment.failed` carrying that response code.

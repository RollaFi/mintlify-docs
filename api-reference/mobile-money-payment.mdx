## Overview

Accept payments from mobile money wallets in Ghana, Senegal and Benin. Most wallets send the customer a prompt on their phone, which they approve with their mobile money PIN. Some finish on the wallet's own page instead — see [Payment flows](#payment-flows).

**Currencies:** `GHS` (Ghana) and `XOF` (Senegal, Benin). The API does not restrict the currency itself — which ones you can charge depends on the mobile money processors enabled on your account. Contact support to confirm what is enabled for you.

<Warning>
  The wallet to debit goes in **`mobileMoney.phone`**, not `customer.phone`. `customer.phone` is stored as a contact detail and is never sent to the processor — a request without `mobileMoney` is rejected with a 400.
</Warning>

## Wallets by country

In **XOF countries, `mobileMoney.provider` is required** and must be one of the identifiers below. It selects both the wallet and the country, so there is nothing else in the request that says where the payment is for.

| Country | Wallet | `provider` | Flow |
|---------|--------|-----------|------|
| Senegal | Orange Money | `orange-senegal` | Redirect to Orange |
| Senegal | Wave | `wave-senegal` | Redirect to Wave |
| Benin | MTN Mobile Money | `mtn-momo-benin` | Prompt |
| Benin | Moov Money | `moov-benin` | Prompt |
| Ghana | MTN, Vodafone, AirtelTigo | `MTN`, `VODAFONE`, `AIRTELTIGO` | Prompt |

Rather than hardcoding this table, call [List Mobile Money Providers](/api-reference/mobile-money-providers) — it returns the wallets currently live in a country, and tells you which flow each one uses.

<Note>
  Togo is not live yet. Charging one of its wallets returns a `503` naming the wallet — call [List Mobile Money Providers](/api-reference/mobile-money-providers) to see what is live rather than assuming from this table, since countries are enabled without a change to these docs.
</Note>

<Note>
  Benin's wallets cap a single charge: **100 to 3,000,000 XOF**. Senegal and Ghana have no such limit.
</Note>

## Amounts in XOF

The West African CFA franc has no subunit — there is no such thing as half a franc. **Amounts must be whole numbers**, and a decimal is rejected rather than rounded:

```json
{ "success": false, "message": "amount: XOF has no subunit — amount must be a whole number. Received 1000.5" }
```

Naira, cedis and every other currency are unaffected and still take decimals as before.

## Authentication

All requests must include your secret API key in the Authorization header:

```
Authorization: Bearer sk_live_your_secret_key
```

<Note>
  Use `sk_test_*` keys for testing and `sk_live_*` keys for production.
</Note>

  <Expandable title="properties">
    <ParamField body="phone" type="string" required>
      The mobile money wallet number, including country code (e.g., `233241234567` for Ghana, `254712345678` for Kenya). Max 20 characters.
    </ParamField>
    <ParamField body="provider" type="string">
      Which wallet to debit — see [Wallets by country](#wallets-by-country). **Required in XOF countries**, where it also selects the country. Optional in Ghana, where the processor resolves it from the number. Max 50 characters.
    </ParamField>
    <ParamField body="customerCode" type="string">
      A pre-authorisation code the customer generates on their handset before the charge, used by wallets on the `pre_otp` flow. Required only where [List Mobile Money Providers](/api-reference/mobile-money-providers) reports `flow: "pre_otp"` — it also returns the `ussd_code` to dial. **No wallet requires it in production today**; send it only when the providers endpoint asks for it.
    </ParamField>
  </Expandable>
</ParamField>

<ParamField body="customer" type="object" required>
  Customer information
  <Expandable title="properties">
    <ParamField body="email" type="string" required>
      Customer's email address
    </ParamField>
    <ParamField body="name" type="string">
      Customer's full name
    </ParamField>
    <ParamField body="phone" type="string">
      Contact phone number. **Not used to debit the wallet** — put that in `mobileMoney.phone`. Max 20 characters.
    </ParamField>
  </Expandable>
</ParamField>

<ParamField body="callbackUrl" type="string" required>
  URL to redirect the customer after payment completion. Query parameters `reference` and `status` (successful/failed) will be appended.
</ParamField>

<ParamField body="description" type="string">
  Optional description for the payment (max 500 characters)
</ParamField>

<ParamField body="metadata" type="object">
  Additional key-value pairs to attach to the transaction (e.g., order ID)
</ParamField>

## Response

<ResponseField name="success" type="boolean">
  Indicates if the request was successful
</ResponseField>

<ResponseField name="message" type="string">
  Response message
</ResponseField>

<ResponseField name="data" type="object">
  <Expandable title="properties">
    <ResponseField name="reference" type="string">
      Unique transaction reference or your custom reference if provided
    </ResponseField>
    <ResponseField name="status" type="string">
      `pending` — a prompt is on the customer's phone and you are waiting for them to approve it. `requires_action` — the customer has to finish on the wallet's own page, at `payment_url`.
    </ResponseField>
    <ResponseField name="payment_url" type="string">
      Present only when `status` is `requires_action`. Send the customer here to complete the payment. Returning from it does **not** mean the payment succeeded — confirm with [Verify Transaction](/api-reference/verify-transaction) or wait for the webhook.
    </ResponseField>
  </Expandable>
</ResponseField>

<Note>
  The initiate response is intentionally minimal. To see the decline reason, AVS/CVV results or any other detail, call [Verify Transaction](/api-reference/verify-transaction).
</Note>

## Payment flows

There are three, and which one a payment takes is a property of the wallet, not of your request. **In XOF countries, ask before you charge:** call [List Mobile Money Providers](/api-reference/mobile-money-providers) for the country and read `flow` on the wallet the customer picked. It tells you what your form has to collect, and it is the only reliable source — wallets change flow without a change to these docs.

| `flow` | Collect before charging | After you charge |
|--------|------------------------|------------------|
| `stk` | Phone number | A prompt appears on the handset |
| `pre_otp` | Phone number **and** a code the customer generates by dialling `ussd_code` | A prompt appears on the handset |
| `redirect` | Phone number | Send the customer to `payment_url` from the charge response |

In Ghana this step is optional — every wallet there is `stk` and `mobileMoney.provider` is resolved from the number.

### `stk` — prompt on the phone

1. **Charge** with `mobileMoney.phone` and, in XOF, `mobileMoney.provider`.
2. **The prompt arrives** on the handset on its own. Nothing to redirect to.
3. **The customer approves it** with their mobile money PIN.
4. **You find out** by [webhook](/api-reference/webhooks), or by polling [Verify Transaction](/api-reference/verify-transaction) every 3–5 seconds until `status` is `successful`.

### `pre_otp` — code first, then prompt

1. **Show the customer the `ussd_code`** from the providers endpoint and have them dial it. The wallet returns a short code.
2. **Collect that code on the same screen as the phone number.** A customer who leaves to dial a USSD string mid-checkout will not reliably come back.
3. **Charge** with the code in `mobileMoney.customerCode`. Without it the request is rejected with a 400.
4. From there it is the `stk` flow — a prompt on the handset, approved with a PIN.

### `redirect` — finish on the wallet's own page

1. **Charge** with `mobileMoney.phone` and `mobileMoney.provider`.
2. **The response comes back `requires_action`** carrying a `payment_url`.
3. **Send the customer there.** They finish in the wallet's app or on its site.

<Note>
  `stk` and `redirect` ask the customer for exactly the same thing, so a wallet reporting `stk` can still come back `requires_action`. Branch your **form** on `flow`, but branch what you do **after charging** on the response: `pending` means the prompt is already on the phone, `requires_action` means you have somewhere to send them.
</Note>

<Warning>
  The customer coming back from `payment_url` does not mean they paid. Confirm with the webhook or Verify Transaction before releasing anything.
</Warning>

## Expiry

A mobile money payment stays open for **15 minutes**, in both XOF and GHS. If the customer never approves it, the transaction is marked **`failed`** with a `response_code` of `EXPIRED`, which is how you tell an abandoned payment from a declined one on [Verify Transaction](/api-reference/verify-transaction).

Start a new transaction rather than retrying; a reference cannot be reused.

Webhooks fire on `pending`, `successful` and `failed`. There is no separate expiry event — an expired payment is a `payment.failed` carrying that response code.
